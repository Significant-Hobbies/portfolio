## The problem

I could describe attention with a diagram, but I could not write its backward
pass from memory. Calling an LLM API did not answer the question I wanted to
understand. What does it take to implement and verify a transformer myself?

I built a small, byte-level GPT that trains in a browser. The WASM and WebGPU
paths use backward passes I derived and wrote by hand. PyTorch is the reference
that lets me compare those implementations against autograd.

## Architecture

The same model exists at three levels, in build order.

- **PyTorch reference.** Model, training loop, sampling, LoRA and evaluation.
  This implementation gives the other two an independent numerical reference.
- **C++ compiled to WebAssembly.** Every backward pass is explicit. Scalar and
  SIMD builds let me compare two CPU execution paths in the browser.
- **WebGPU and WGSL.** Forward passes, backward passes and AdamW run on the GPU.
  Tensors remain in GPU buffers, a pool reuses memory, and one training step
  records into one command submission.

The browser runs training in a Web Worker. Checkpoints use OPFS so a run can
survive a refresh. The public site also exposes the learning paths and recorded
experiments behind the project.

## How I checked the implementation

A finite-difference gradient check compares each hand-written backward pass
with a numerical estimate. A separate overfit gate asks whether the full model
can learn one batch. These checks answer different questions. A correct local
derivative is necessary, but a complete training loop must also update the
right parameters and reduce loss.

I built the PyTorch reference first, then WASM, then WebGPU. Each stage had a
working implementation to compare with. The GPU work shipped in bounded
pieces, including tensor operations, attention, embeddings, the loss function,
AdamW, and the training orchestrator.

An early automated comparison reported WebGPU slower than WASM. The browser
was using SwiftShader, a software adapter. That measured software WebGPU
against SIMD WASM. I withdrew the hardware interpretation and kept the failure
in the project record.

## What the browser benchmark actually measured

The retained hardware run was recorded on **2 September 2026**, on **one Apple
M5 Pro in Chrome 151**. It compared the **Large preset**, using six layers,
width 192, context 128 and batch size 12. The sequence was WASM, WebGPU,
WebGPU, WASM, with 20 training steps per arm.

The recorded median time per step was **1,462.50 ms for WASM** and **137.08 ms
for WebGPU**, a **10.67× ratio for this workload**. The maximum paired final-loss
relative drift was **4.72%**. Those numbers describe this short paired run.
They do not establish the same ratio on other presets, longer training runs,
other browsers or other hardware.

Read the [immutable paired-result artifact](https://github.com/PostTrainLLM/posttrainllm/blob/a7f3a54dd9310dcd70d208763c4332ab4917623d/evals/verified-wins/webgpu-paired-result-v1.json)
for the four individual arms, adapter checks, input hashes and tested source
revision. The [paired-run contract](https://github.com/PostTrainLLM/posttrainllm/blob/a7f3a54dd9310dcd70d208763c4332ab4917623d/evals/verified-wins/webgpu-v1.json)
records the acceptance gates. This is a historical measurement, not a new
benchmark run or a general WebGPU speed claim.

## What local post-training taught me

The same verification approach carried into a Mac-first MLX-Swift project for
data preparation, LoRA post-training, evaluation, packaging, and an
OpenAI-compatible local server.

One recorded experiment distilled Qwen3-4B-2507 from about 99 frontier
trajectories. It completed **12 of 12 tasks on a GorillaFileSystem multi-turn
hard gate**, matching the DeepSeek-V4-pro anchor on that gate. The stock 4B
with a planning prompt scored 75%, and zero-shot Gemma-4-12b-qat scored 83%.
This compared a domain-specialized model with general models. It was not a
claim of general frontier parity.

The same record reports 95% on a 40-task held-out set and a single-turn BFCL
average that fell from about 87 to 83. Narrow specialization had a cost.
Generalization to unrelated agent backends was untested in that experiment.
The [immutable frontier-parity report, sections 8.1 and 8.2](https://github.com/PostTrainLLM/posttrainllm/blob/a7f3a54dd9310dcd70d208763c4332ab4917623d/docs/learn/tool-calling-frontier-parity.md)
contains the recipe, comparison and caveats. These are recorded project
results, not promises about another product's shipped model.
